# Security operations: controls, scanning and findings report

Covers brief topic #11 and the Security Baseline (section 6). Each control points to the code that implements it,
and to the evidence to capture for the final presentation.

## 1. Controls against the security baseline

| Baseline item | Implementation | Code | Evidence to capture |
|---|---|---|---|
| Least-privilege IAM | One IRSA role per service account: `usage-api` can only `SendMessage` to its queue, `notification-service` can only receive/delete; LB controller, EBS CSI, CloudWatch agent and Alertmanager have their own roles | `terraform/main.tf`, `modules/irsa` | IAM console: role policies; `kubectl describe sa usage-api` |
| Kubernetes RBAC | EKS access entries only (no `aws-auth`). The CI deploy role has `AmazonEKSEditPolicy` **scoped to one namespace**; cluster-admin only for listed admins | `modules/eks`, `modules/github_oidc` | `aws eks list-access-entries`, `kubectl auth can-i --as ...` |
| No hardcoded credentials, no long-lived CI keys | GitHub OIDC: push role trusts `ref:refs/heads/main` only, deploy role trusts `environment:<env>` only; pods use IRSA; no AWS keys in GitHub | `modules/github_oidc`, `.github/workflows/` | Repository settings show no AWS secrets; CloudTrail `AssumeRoleWithWebIdentity` events |
| Secrets Manager / KMS | DB URL generated by Terraform, stored in Secrets Manager (CMK), synced to a Kubernetes Secret; Kubernetes secrets envelope-encrypted with KMS; SQS, SNS, RDS, ECR, logs, CloudTrail, EBS encrypted | `modules/rds`, `modules/kms`, `modules/eks` | `aws secretsmanager describe-secret`, EKS encryption config |
| Trivy container/dependency scanning | Image scan on every build (OS + Python packages): fixable CRITICAL blocks the release; repo scan for secrets (blocking) and misconfigurations (reported) | `.github/workflows/ci-cd.yml` | Actions run, GitHub *Security > Code scanning* |

| GuardDuty, Inspector, Security Hub | GuardDuty (+ EKS audit logs, S3 data events), Inspector (ECR + EC2), Security Hub (AWS Foundational Security Best Practices) | `modules/security` | Security Hub summary score, GuardDuty findings (sample findings for the demo) |
| Workload hardening | Non-root UID 10001, read-only root filesystem, all capabilities dropped, seccomp RuntimeDefault, no service-account token, NetworkPolicy default deny, chaos endpoints off in prod and never routed by the Ingress, phone numbers masked in logs | `charts/telecom-app` | `kubectl get pod -o yaml`, `kubectl get networkpolicy` |
| Ownership of findings | Every alert carries `owner`; this document holds the findings register and triage rules | `files/rules`, below | This page |

## 2. How scanning gates delivery

| Scanner | Scope | Blocks the pipeline | Reported to code scanning |
|---|---|---|---|
| Trivy (image) | each service image | fixable **CRITICAL** CVEs | CRITICAL + HIGH |
| Trivy (repo) | secrets | any committed secret | - |
| Trivy (repo) | IaC misconfig + dependencies | no | CRITICAL + HIGH |
| Checkov | Terraform, rendered manifests, Dockerfiles, workflows | no (soft fail, see below) | all failed checks |

Checkov starts as **report-only** because the first run in a new environment needs a triage pass. Once the register
below is clean, remove `soft-fail: true` from `.checkov.yaml` and `soft_fail: true` from the workflow so new findings
block pull requests.

## 3. Triage rules

| Severity | Fix within | Who | Allowed outcome |
|---|---|---|---|
| Critical | before the next release (the image gate enforces it) | owning team | fix, or documented exception approved by platform-sre |
| High | 14 days | owning team | fix, accept with expiry date, or false positive |
| Medium / Low | backlog, reviewed monthly | owning team | any, documented |

Owners follow the alert labels: `platform-sre` (cluster, network, IAM, CI/CD), `notifications-team`
(notification-service, queue), `data-platform` (RDS, database access), application team for `usage-api`.

An accepted risk is written in three places: the register below, the scanner's ignore file (`.trivyignore` with an
`exp:` date, or `.checkov.yaml` with a reason), and the pull request that added it.

## 5. Known gaps (honest list for the risks slide)

- Database password is generated by Terraform and therefore present in (encrypted, private) Terraform state.
- No WAF in front of the ALB, and the demo ALB is HTTP only (no domain / ACM certificate).
- Egress is not restricted by NetworkPolicy (only ingress), and there are no VPC interface endpoints.
- AWS Config is not enabled, so part of Security Hub's controls cannot evaluate.
- Python dependencies use lower bounds; images are reproducible per SHA, but the lock is the image itself.
